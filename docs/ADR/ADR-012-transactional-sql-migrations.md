# ADR-012: Ordered transactional SQL migrations

**Status:** Implementation decision authorized; pending human review
**Date:** 2026-10-10

## Decision

Use pg and tracked numbered SQL files, without an ORM. An explicit compiled
NodeNext CLI selects only the dedicated local synvora_dev or synvora_test target.
Startup checks checksums/schema readiness and never applies migrations implicitly.

Migration files have unique three-digit prefixes and deterministic filename order.
A dedicated connection holds a session advisory lock for discovery-history
verification and application. Each migration's DDL and tracking row commit in
one transaction. A failed migration rolls back both; prior successful migrations
remain applied. Applied files cannot be removed, changed, or preceded by a newly
inserted migration. Checksums are SHA-256 over exact file bytes.

The SQL directory is a tracked runtime asset alongside compiled application output.
It is resolved from import.meta.url, independent of the CLI working directory.
Historical migrations are immutable; corrective changes require new migrations.
No automatic down/reset command is provided.

## Local isolation

Docker Compose provisions two distinct PostgreSQL 17.6 containers, volumes,
credentials, and localhost ports: synvora_dev on 55432 and synvora_test on 55433.
POSTGRES_DB creates each database on first initialization of a fresh volume.
Existing volumes are never reset to force initialization. Missing databases on
existing volumes require inspection and explicit non-destructive provisioning.

Database tests verify the actual database identity, create random isolated schemas
inside synvora_test, and remove only the schemas generated by that test execution.
They do not truncate public tables or touch synvora_dev. Migration failure tests
use temporary SQL fixtures inside isolated schemas.

## Consequences

Migration execution needs explicit database-modification approval during agent work.
Versioned database schema is retained across application restarts. Docker health
checks do not replace real connection, database identity, and schema verification.
